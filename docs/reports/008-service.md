## 구조

```
collector-jaeung → collector.db (SQLite WAL, 서비스는 읽기 전용으로 연다)
inference-jaeung (매분)
  1. 최근 26시간 읽기 → 끝난 5분 칸까지만
  2. pipeline.preprocess (과제 2와 같은 함수: 중복 제거, 범위·고정값 제거, 센서 10분 유지, 공간 중앙값)
  3. 공간마다 예측(ONNX) · 이상 점수(ONNX) + 규칙 · 분류기 · 센서 끊김
  4. 결과 → MQTT retained, HTTP API, 대시보드(/), 주기 기록 cycles.csv
```

## 학습과 서비스가 같은 전처리를 거쳐야 하는 이유 (해결할 것 3)

서비스는 학습 코드와 **같은 파일의 같은 함수**를 부르고, 정규화 값도 학습 기간에서 계산해 둔 `normalization.json`을 그대로 쓴다. 다르면 모델은 학습 때 본 적 없는 입력을 받는다. 그런데 오류는 나지 않고 그럴듯하게 틀린 숫자만 나온다. 이번 과제에서 실제로 겪었거나 겪을 뻔한 예는 아래와 같다.

| 전처리 차이 | 생기는 일 | 근거 |
| --- | --- | --- |
| 센서 10분 유지를 서비스에서 빼면 | 실습실 10분 센서가 들어오고 빠질 때마다 공간 중앙값이 오르내린다. 5분 예측 오차가 30분 예측보다 커졌던 문제(과제 2)가 서비스에서만 다시 생긴다 | `002-diagnosis.md` |
| 정규화를 최근 데이터로 다시 계산하면 | 같은 900 ppm이 다른 z값이 된다. 모델은 "평소보다 높다/낮다"를 잘못 읽는다. 과제 4에서는 이상 점수의 기준이 흔들려 임계값이 무의미해진다 | 헌법 원칙 2 |
| 반쯤 찬 5분 칸을 쓰면 | 학습 표본은 `[t−5, t)` 칸이 다 찬 중앙값이다. 칸이 덜 차면 측정 1~2개로 값이 정해져 잡음이 커진다. 경계에서 값이 튀는 것처럼 보인다 | `service/engine.py` `read_raw` |
| 중복 메시지 제거를 빼면 | 같은 값이 두 번 들어가 중앙값이 그 센서 쪽으로 쏠린다. 과제 1에서 4분에 4건 관찰했다 | `001-findings.md` 발견 2 |
| 시각 기준을 게이트웨이 시각으로 쓰면 | 한 게이트웨이가 5분 빠르다. 메시지가 엉뚱한 칸에 들어가고 CO₂ 반응 시점이 틀어진다 | `001-findings.md` 발견 1 |

그래서 모델 묶음(`export`)에는 모델과 함께 정규화 값, 규칙 기준값, 임계값, 학습 코드 커밋을 넣는다. 분류기 피클은 scikit-learn 버전이 다르면 서비스가 시작을 거부한다.

## 생각해 볼 점

- **막 시작된 5분 칸을 써도 되나?** 쓰지 않는다. 학습 표본은 다 찬 칸의 중앙값이라, 1~2분치 칸은 학습 때와 다른 입력이 된다. 그래서 서비스는 `floor(지금, 5분)`까지 끝난 칸만 읽는다. 계산은 매분 하지만 예측값은 5분마다 바뀐다. 대신 끊김 경보는 1분 단위로 빨리 낸다. 센서 수신 시각은 칸과 상관없이 바로 볼 수 있기 때문이다.
- **같은 고장에 매분 경보를 보내면?** 1시간이면 60건이 쌓인다. 받는 사람은 경보를 무시하게 되고, 그 사이에 새 경보가 묻힌다(과제 4에서 경보를 묶은 이유와 같다). 그래서 (공간, 종류)마다 처음 생길 때 `active`, 계속되면 30분마다 `repeat`, 사라지면 `cleared`를 한 번씩 보낸다. 현재 상태가 필요하면 retained `state`나 API `alerts`를 본다.
- **로컬 LLM이 이 서비스를 도구로 쓰려면?**
  - 지금 있는 것: 단위, 기준 시각(`slot`, `as_of`), 끊김 이유(`forecast_unavailable`), 경보 문장(`message`).
  - 더 있으면 좋은 것:
    - 예측 불확실성(과제 6의 q10/q90처럼 구간)
    - 모델의 평소 오차("이 공간 60분 예측은 보통 ±30 ppm")
    - 최근 몇 시간의 실제값 이력 API
    - 경보 근거 숫자(어떤 규칙이 어떤 기준값을 넘었는지)
    - 공간 정보(정원, 환기 장치 유무)
  - LLM은 숫자를 지어내기 쉽다. 그래서 "모름"을 뜻하는 필드(`null`과 이유)를 분명히 주는 것이 가장 중요하다.

## 해석과 다음 할 일

**1. 서비스는 멈추지 않았다.** 19.7시간 동안 1,182주기를 모두 계산했다. 한 주기 1.3초 중 ONNX 예측은 1 ms 미만이므로(과제 7), 나머지는 26시간치 DB 읽기와 전처리로 본다(추정, 단계별 시간은 따로 재지 않음). 60초 주기 안에서 여유가 크다.

**2. 예측 기반 경보는 맞고, 분류기 환기 경보는 너무 이르다.**
- `co2_forecast`("몇 분 뒤 1,000 ppm 초과")는 4건 모두 실제로 1,000 ppm에 닿았다.
- `ventilation`(분류기 "30분 안 초과")은 5건 중 1건만 맞았다. 틀린 4건도 최대 826~910 ppm까지는 올랐다. 과제 5에서 본 낮은 정밀도(16.5%)가 운영에서도 그대로 나온 것이다. 재현율 85%를 맞추려고 임계값을 낮게 잡은 대가다.
- **그래서:** 사람에게 보내는 알림은 `co2_forecast`를 기본으로 하고, `ventilation`은 "주의" 단계로 낮춘다. 과제 5 "생각해 볼 점"의 두 단계 경보와 같은 결론이다.

**3. `forecast_drift`가 많다(회의실 850주기).** 60분 전 예측과 실제의 차이가 커지면 내는 자체 감시 경보다. 회의실은 10분 간격 센서이고 회의가 일정 없이 시작돼 예측 오차가 크다(과제 3에서 큰 오차 상위 50개 중 39개). 회의실 기준을 따로 잡거나, 사람에게 보내지 않는 정보 단계로 두는 것이 맞다.

**4. 남은 확인 기준:** 수집기 10분 정지 시험. 보드 A에서 사용자가 `sudo systemctl stop collector-jaeung` → 10분 → `curl -s localhost:8080/v1/alerts`로 `data_gap` 확인 → `sudo systemctl start collector-jaeung` → 몇 분 뒤 `cleared` 확인.
