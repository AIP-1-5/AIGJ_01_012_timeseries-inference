# Research: 과제 1 — 데이터 수집 체계

근거 자료: `spec.md`, `../docs/environment.md`의 "MQTT 메시지 형식"(2026-10-20~21 보드 B 관찰), constitution v1.0.1.

## R1. 언어와 의존성

- **Decision**: Python 3.12(Ubuntu 24.04 기본) + 계정별 `.venv`. 외부 패키지는 `paho-mqtt` 하나만 쓴다. 설정은 표준 라이브러리 `tomllib`(TOML), 저장은 표준 라이브러리 `sqlite3`. 테스트는 `pytest`(개발용).
- **Rationale**: 보드는 ARM64라 바이너리 휠 호환이 걱정인데, `paho-mqtt`는 순수 Python이라 문제가 없다. 의존성이 적을수록 보드 A로 옮길 때 깨질 곳이 줄고 메모리도 적게 쓴다(constitution VII, 운영 제약의 메모리 예산).
- **Alternatives**: YAML 설정(PyYAML 추가 필요, TOML로 충분), `python-dotenv`(systemd `EnvironmentFile`과 셸 `source`로 대체 가능).

## R2. 저장소

- **Decision**: 보드 로컬 SQLite 파일 1개, WAL 모드. 기본 경로는 저장소의 `data/collector.db`(`.gitignore` 대상), 설정으로 바꿀 수 있다. 보드 A 운영 시 `/srv/team5/collector/collector.db` 같은 공용 경로로 지정한다.
- **Rationale**: 센서 약 15대 × 분당 1건 수준이라 SQLite로 충분하다. WAL 모드는 읽는 쪽(현황 조회, 내보내기, 학습용 추출)이 쓰는 쪽(수집기)을 막지 않는다(FR-013, SC-007). 별도 DB 서버가 없어 장애 지점이 줄고 재부팅 후에도 바로 열린다.
- **Alternatives**: 로컬 InfluxDB·PostgreSQL 설치(관리할 서비스가 하나 더 생김), CSV 파일 누적(중복 제거·동시 읽기·조회가 어렵다), 교육장 InfluxDB에 쓰기(용도 미정이고 토큰이 읽기용일 가능성, 쓰지 않기로 spec에서 정함).

## R3. 기준 시각

- **Decision**: 측정값마다 시각 3개를 저장한다.
  - `measured_at`: `rxInfo[].nsTime` 중 가장 이른 값(네트워크 서버 시각). **분석과 커버율의 기준 시각.**
  - `gw_time`: 메시지 최상위 `time`(게이트웨이 시계, 참고용).
  - `received_at`: 보드가 받은 시각(보드 시계).
- **Rationale**: 2026-10-20 관찰에서 게이트웨이 `24e124fffef5dccc`의 시계가 약 5분 빨랐고, 메시지 최상위 `time`이 그 게이트웨이 시각을 따라 뒤죽박죽이었다. `nsTime`은 같은 메시지를 받은 게이트웨이가 달라도 일관됐다. 세 시각을 다 남기면 네트워크 지연(과제의 "30초 밀려 한꺼번에 도착")과 시계 오차를 나중에 계산할 수 있다.
- **Alternatives**: `received_at`만 저장(재전송·밀림이 시각을 왜곡), `time`만 저장(게이트웨이 시계 오류를 그대로 받음).
- **Fallback**: `nsTime`이 없는 메시지는 `received_at`을 `measured_at`으로 쓰고 `time_source` 열에 표시한다.

## R4. 중복 제거

- **Decision**: 메시지 키 = `deduplicationId`(없으면 `devEui` + `fCnt` + `measured_at`의 분). `(message_key, metric)`에 UNIQUE 제약을 두고 `INSERT OR IGNORE`로 넣는다. 무시된 건은 `duplicates` 표에 시각과 키를 남겨 하루 중복 건수를 보고한다.
- **Rationale**: 2026-10-21 관찰에서 같은 메시지가 4분에 4건 두 번 도착했다. 그대로 저장하면 건수와 학습 데이터가 부푼다. 중복 처리는 과제 1 심화 항목이지만 실제로 일어나므로 기본 구현에 넣는다. 저장 단계에서 걸러도 원본 정보 손실은 없다(완전히 같은 메시지이므로).
- **Alternatives**: 나중에 과제 2에서 정리(건수·커버율 보고가 부정확해짐).

## R5. 재연결과 "조용한 끊김"

- **Decision**:
  - `paho-mqtt`의 자동 재연결을 쓰고 재시도 간격을 1초에서 시작해 최대 20초로 제한한다. 브로커가 돌아온 뒤 다음 재시도까지 최대 20초라 1분 기준(FR-006)을 여유 있게 지킨다.
  - 고정 client ID(설정값, 사람·보드마다 다르게)와 `clean_session=False`, QoS 1 구독으로 브로커가 짧은 끊김 동안 메시지를 보관해 주면 받아 온다(브로커가 지원하는 범위에서). 이로 생기는 재전송은 R4가 거른다.
  - 감시: 연결 상태로 보이는데 설정 시간(기본 5분) 동안 아무 메시지도 없으면 스스로 연결을 끊고 다시 붙는다.
  - 프로세스가 죽으면 systemd가 다시 띄운다(R6).
- **Rationale**: 확인 기준 1과 FR-006·FR-007. 공용 계정(`academy`)을 여러 학생이 같이 쓰므로 client ID가 겹치면 서로 접속을 끊어 버린다. client ID를 `team5-<보드>-<사용자>-collector` 형식으로 정해 충돌을 막는다.
- **Alternatives**: 재시도 간격을 지수적으로 무제한 증가(복구 후 1분을 넘길 수 있음).

## R6. 자동 시작

- **Decision**: systemd 시스템 서비스. `Restart=always`, `RestartSec=5`, `After=network-online.target`, `User=<실행 계정>`, `EnvironmentFile=<저장소>/.env`, `WorkingDirectory=<저장소>`. 저장소에는 템플릿(`deploy/collector.service`)과 설치 스크립트(`deploy/install-service.sh`, sudo 한 번 필요)를 둔다.
- **Rationale**: 확인 기준 2(재부팅 후 로그인 없이 자동 시작), FR-007(비정상 종료 시 자동 재실행). constitution VI가 systemd를 명시한다.
- **Alternatives**: 사용자 서비스 + `loginctl enable-linger`(결국 sudo 필요, 시스템 서비스가 더 단순), cron `@reboot`(죽었을 때 재시작 안 됨).

## R7. 설정으로 형식 대응

- **Decision**: `config/collector.toml`에 "소스"를 여러 개 정의한다. 소스마다 구독 토픽, 메시지 안의 위치(점 경로, 예: `deviceInfo.tags.location`), 측정값 묶음 위치(`object`), 저장할 항목 목록과 이름 바꾸기, 단위, 중복 키 경로를 적는다. 센서별 기대 전송 간격은 센서 종류 기본값 + 장비별 덮어쓰기로 적는다.
- **Rationale**: 해결할 것 2, FR-004·FR-005. 실제로 센서 종류마다 보내는 항목이 다르고(AM103/AM107/EM500-CO2/EM300-TH 등), 냉난방(`xflow/...`) 같은 다른 형식도 같은 브로커에 있다. 나중에 소스를 하나 추가하는 것만으로 대응할 수 있다.
- **Alternatives**: 코드에 형식을 박아 넣기(요구사항 위반).
- **산출물 연결**: "형식 변경 대응 기록"은 시험용 로컬 브로커에 바뀐 형식(필드 이름 변경)을 보내고 설정만 고쳐 대응하는 과정으로 만든다(R9).

## R8. 커버율과 결측 원인

- **Decision**:
  - 커버율 = 기간을 센서의 기대 간격(기본 1분)으로 나눈 칸 중 `measured_at`이 1건 이상 있는 칸의 비율. 센서·항목별로 내고 공간별로 묶는다. 1분 기준 값도 함께 보고한다.
  - 결측 구간 = 연속으로 빈 칸이 기대 간격의 2배 이상인 구간.
  - 원인 추정 규칙(위에서부터 먼저 맞는 것):
    1. 그 시간대에 수집기 사건(정지·끊김)이 있음 → **수집기 쪽**
    2. 구간 앞뒤 `fCnt` 차이가 2 이상(보낸 메시지가 사라짐)이고 수집기는 정상 → **무선·게이트웨이·서버 쪽 손실**
    3. `fCnt`가 이어짐(센서가 보내지 않음) → **센서 쪽**(배터리 값이 낮으면 배터리로 표시)
  - 같은 시간대 교육장 InfluxDB에 값이 있는지 비교하는 기능은 선택(보드에 유선 경로가 있을 때만).
- **Rationale**: 확인 기준 3("빠진 구간이 있으면 원인을 설명")과 FR-010·FR-011. 관찰된 간격이 1분·2분·10분으로 달라 1분 고정이면 10분 센서는 커버율이 최대 10%가 된다. `fCnt`는 센서가 메시지마다 1씩 올리는 번호라 손실 위치를 가를 수 있다. 사무실 AM103 배터리가 1%라 실제로 쓸 일이 생길 가능성이 크다.

## R9. 장애 시험 방법

- **브로커 꺼짐(SC-001)**: 공용 브로커를 끌 수 없으므로 보드 B에서 나가는 1883 포트를 `iptables`로 막았다 푼다. 푼 시각부터 첫 새 저장까지를 잰다. 3회 반복.
- **네트워크 끊김(SC-004)**: 같은 방식. 와이파이를 끄면 SSH가 끊기므로 쓰지 않는다.
- **재부팅(SC-002)**: 보드 B에서 `sudo reboot`. 부팅 완료 시각(`systemctl show`·`uptime -s`)부터 첫 새 저장까지를 잰다. 보드 A는 재부팅 금지라 같은 서비스 파일을 그대로 쓴다.
- **형식 변경(SC-005)**: 보드 B에 시험용 로컬 브로커(`mosquitto`)를 띄우고, 두 번째 설정 파일로 수집기를 붙인 뒤 `mosquitto_pub`으로 바뀐 형식을 보낸다. 운영 수집기는 건드리지 않는다.
- **동시 읽기(SC-007)**: 수집 중 전체 내보내기를 돌리고 그 시간대 커버율을 전후와 비교한다.
- **24시간 커버율(SC-003)**: 보드 B에서 서비스로 24시간 이상 돌린 뒤 `report` 명령으로 보고서를 만든다. 최종 운영은 보드 A에서 같은 방법으로 다시 확인한다.

## R10. 남은 확인 사항 (계획을 막지 않음)

- 보드 A에서 MQTT(1883) 접속 여부: 배포 전에 `nc -zv -w 5 data.withio.net 1883`으로 확인한다.
- 브로커가 `clean_session=False` 세션 보관을 지원하는지: 지원하지 않아도 동작에는 문제 없고 끊김 동안의 메시지만 못 받는다. 시험에서 확인해 보고서에 적는다.
- 교육장 InfluxDB에 우리 결과를 써야 하는지: 강사 답변 대기. 쓰라고 하면 저장 대상을 하나 추가하는 방식으로 붙인다(R2 구조 유지).
