# Research: 과제 2 — 데이터 이해와 기준선

근거: `spec.md`, `../docs/environment.md`(InfluxDB 구조, MQTT 관찰), 과제 1 발견 기록(`docs/reports/001-findings.md`), constitution v1.0.1.

## R1. 데이터 가져오기

- **Decision**: 보드 B에서 InfluxDB `iot-bucket`을 월 단위로 조회해 CSV.gz로 내보내고(`co2`, `temperature`, `humidity`, `battery`), `scp`로 맥에 옮겨 분석한다. 조회는 표준 라이브러리 `urllib`로 InfluxDB HTTP API(Flux, CSV 응답)를 부른다.
- **Rationale**: InfluxDB는 보드 B 유선으로만 닿는다. 분석·그래프는 메모리를 아끼기 위해 맥에서 한다(팀 역할 분담). 월 단위로 끊으면 한 번의 응답이 작고, 실패해도 그 달만 다시 받으면 된다. 보드에 추가 패키지를 설치하지 않는다.
- **Alternatives**: `influxdb-client` 패키지(의존성 추가, 보드 B에만 필요), 과제 1 수집기 데이터만 사용(이틀치뿐이라 학습·평가 기간이 안 나옴).

## R2. InfluxDB 시각 확인

- **Decision**: 과제 1 수집기와 InfluxDB가 겹치는 기간(2026-10-21 이후)에 같은 센서·항목 값을 짝지어 시각 차이 분포를 잰다. 차이가 0에 가까우면 그대로 쓰고, 일부 센서에서 약 5분 차이가 나면(시계가 틀린 게이트웨이) 진단서에 한계로 적고 처리 방법을 정한다.
- **결과 (2026-10-21, 보드 B `check-time`)**: 최근 기록 5,727행이 12대 모두 100% 짝지어짐, 차이 0.2초(10~90% 모두 0.2초). InfluxDB는 서버가 받은 순간 시각으로 저장하며 게이트웨이 시계를 따르지 않는다 → 보정 없이 사용.
- **Rationale**: 과제 1에서 게이트웨이 한 대의 시계가 약 5분 빠른 것을 봤다. InfluxDB가 어떤 시각으로 저장했는지 모르면 "일정 뒤 CO₂가 몇 분 만에 반응하나" 분석이 몇 분씩 틀릴 수 있다.

## R3. 언어와 의존성

- **Decision**: Python 3.12(맥·보드 공통, 3.11 호환 유지), `pandas`, `numpy`, `matplotlib`, `holidays`(대한민국 공휴일). 새 패키지 `pipeline/`. 과제 1 수집기(`collector/`)와 분리한다.
- **Rationale**: 시계열 리샘플링·집계에 pandas가 가장 짧고 검증된 방법이다. 네 패키지 모두 macOS arm64와 Linux aarch64용 휠이 있다(과제 8에서 보드가 같은 전처리를 불러 쓸 수 있다). 수집기는 의존성 1개를 유지해야 하므로(과제 1 원칙) 분석 의존성은 `requirements-analysis.txt`로 따로 둔다.
- **Alternatives**: 순수 Python(코드가 길고 틀리기 쉬움), polars(팀이 덜 익숙, 과제 3의 PyTorch 생태계와 pandas가 더 잘 맞음).

## R4. 정제 규칙 (FR-001)

| 규칙 | 기본값 | 이유 |
|---|---|---|
| CO₂ 허용 범위 | 300 ~ 5,000 ppm | 외기가 약 420ppm이라 실내가 300 밑일 수 없다. 0ppm은 깨진 값. 5,000 초과는 실내 센서 측정 범위 밖 |
| 온도 허용 범위 | 0 ~ 45 ℃ | 실내 공간. 60℃ 같은 값은 깨진 값 |
| 습도 허용 범위 | 1 ~ 99 % | 0·100은 센서 오류값으로 자주 나온다 |
| 짧은 결측 | 15분 이하 → 선형 보간 | CO₂·온도는 15분 안에 크게 바뀌지 않는다. 10분 간격 센서는 메시지 1건만 빠져도 20분 빈칸이 생기므로, 5분 격자에서 빈 칸 3개(15분)까지만 채운다 |
| 긴 결측 | 15분 초과 → 결측으로 남김 | 길게 채우면 없는 값을 만들어 기준선·모델 성적이 부풀거나 왜곡된다 |
| 보간 값의 쓰임 | 입력에는 써도 되지만 **정답(평가 대상)으로는 쓰지 않는다** | 보간 값을 정답으로 쓰면 선형으로 맞히기 쉬운 값을 맞힌 셈이라 성적이 좋아 보인다 |
| 센서 ID 없는 행 | 뺀다 | 2025-08 초기 데이터는 `device_id` 태그가 없다(대부분 공간 태그도 없음). 센서를 구분할 수 없어 공간 중앙값을 만들 수 없다. 실제 분석 시작은 2025-09 초 |
| 중복 | 같은 센서가 10초 안에 다시 보낸 기록은 첫 번째만 (범위 제거 뒤) | InfluxDB가 받은 순간 시각으로 저장해 두 번 도착한 메시지가 1초 미만 차이로 둘 다 남는다(2026-03 2분 센서 32,021행 중 10,137건). 전송 간격은 최소 1분 |
| 고장 의심 구간 | 같은 값이 CO₂ 6시간, 온도·습도 24시간 이상 그대로(값 고정) | 과제 4의 "값 고정" 고장. 학습과 평가에서 뺀다(R9). **처음 60분으로 정했다가 실데이터로 바꿨다(2026-10-21)**: 같은 값이 이어진 구간을 세어 보니 24시간 넘는 구간은 하나도 없었고, 가장 긴 구간은 CO₂ 3.3시간(10분 센서, 외기 수준 404ppm), 온도·습도 12~15시간으로 모두 저녁~다음 날 아침(빈방)이었다. 60분이면 온도 0.1℃·습도 1% 해상도 때문에 정상인 밤이 고장으로 잡혔다(회의실 온도 14.5%, 사무실 습도 18.2%). 기준은 정상 최장 구간의 약 2배 |

모든 값은 규칙별로 몇 건을 지웠는지·채웠는지 센다(FR-003).

## R5. 분석 간격과 칸 정하기 (FR-004)

- **Decision**: 5분. 칸 `[t−5분, t)`의 원시 값 평균을 시각 `t`에 붙인다(오른쪽 끝 표기).
- **Rationale**: 과제 3은 5분 간격으로 60분을 예측한다. 2분·10분 센서를 같은 격자에 놓을 수 있다. 1분 잡음이 줄고 데이터 양이 1/5이 된다. 칸의 값이 그 칸이 끝난 시각에 확정되므로, 시각 `t`에서 쓸 수 있는 정보만 시각 `t`에 붙는다(미래 정보가 섞이지 않는다). 과제 8의 "막 시작된 5분 칸" 문제도 이 규칙으로 정리된다.
- **확인**: 1분 그대로와 비교해 하루 패턴 그래프가 같은 모양인지 진단에서 본다.

## R6. 공간 값 만들기 (FR-005)

- **Decision**: 같은 공간·같은 항목 센서들의 5분 칸 값 중 **중앙값**. 쓸 수 있는 센서가 없으면 결측.
- **Rationale**: 실습실은 CO₂ 센서가 3대 이상이다. 한 대가 고장 나도 중앙값은 크게 흔들리지 않는다. 사무실·회의실은 CO₂ 센서가 1대라 그 값이 곧 공간 값이다. 설정 파일에 공간별로 쓸 센서 목록을 적어, 위치가 이상한 센서(예: 복도)를 뺄 수 있게 한다.

## R7. 기간 분할 (FR-006, 완료 조건 1)

- **Decision**: 시간 순서로 학습 → 검증 → 시험. 시험 = 데이터 끝에서 연속 28일, 검증 = 그 앞 28일, 학습 = 나머지(2025-08-08 ~). 경계는 자정(KST) 기준. `artifacts/split.json`에 고정한다.
- **Rationale**: 무작위로 섞으면 이웃한 5분 칸(거의 같은 값)이 학습과 시험에 나뉘어 들어가 시험 성적이 부풀고, 미래 기간의 패턴이 학습에 섞인다. 28일은 평일·주말 4주를 온전히 담는다. 학습에 지난해 가을(2025-09~11)이 들어 있어 시험(2026년 가을)과 계절이 비슷하다.
- **조정**: 진단에서 시험 기간에 큰 결측이나 고장이 몰려 있으면 경계를 옮기고 이유를 적는다. 한 번 고정한 뒤에는 과제 3·4·5·6이 같은 분할을 쓴다.

## R8. 정규화 (완료 조건 1)

- **Decision**: 공간·항목별 평균·표준편차를 **학습 기간의 정제된 관측 값(보간 제외)**으로 계산해 `artifacts/normalization.json`에 저장. 함수는 분할 정의를 받아 학습 기간만 잘라서 계산하고, 자동 시험으로 "검증·시험 값을 바꿔도 결과가 같다"를 확인한다.
- **Rationale**: 시험 기간의 평균·분산을 쓰면 미래 정보가 새어 들어간다(constitution 원칙 II).

## R9. 고장이 섞인 구간 (생각해 볼 점 2)

- **Decision**: 진단에서 값 고정(R4 기준: CO₂ 6시간, 온도·습도 24시간 이상 같은 값)과 밤사이 CO₂ 바닥값이 외기(약 420ppm)보다 크게 높은 날(영점 틀어짐 의심)을 표시한다. 값 고정 구간은 학습과 평가 정답에서 모두 뺀다. 영점 틀어짐 의심은 표시만 하고 진단서에서 판단한다.
- **Rationale**: 학습에 고장을 넣으면 모델이 고장을 정상으로 배운다. 평가에 넣으면 기준선·모델 모두 고장 값을 "맞히는" 이상한 점수가 나온다. 단, 과제 4(이상 탐지)는 고장을 찾아야 하므로 표시 정보를 남겨 과제 4가 쓰게 한다.

## R10. 기준선과 평가 시점 (FR-011·012, 완료 조건 2·3)

- **기준선** (예측 시각 `t`, 몇 분 뒤 `h` ∈ {5, 15, 30, 60}):
  - 현재값 유지: `ŷ(t+h) = y(t)`
  - 최근 1시간 평균: `ŷ(t+h) = mean(y(t−55분 … t))` (12칸)
  - 어제 같은 시각: `ŷ(t+h) = y(t+h−24시간)`
- **평가 시점 규칙**: 시험 기간의 5분 시각 `t` 중
  - `y(t)` 관측(보간 아님), 직전 12칸 중 9칸 이상 값 있음, `y(t+h−24h)`가 모든 `h`에 있음
  - 정답 `y(t+h)`가 모든 `h`에서 관측 값(보간·고장 구간 아님)
- `artifacts/eval_points.csv`(공간, 시각)에 고정한다. 과제 3·6의 모델도 이 파일로 평가한다(SC-002). 같은 파일로 다시 돌리면 같은 숫자가 나와야 한다(SC-007).
- **보고**: 공간별·전체 MAE(원래 단위)와 평가 시점 수. 해석을 돕기 위해 "평일 실습 시간(09:00~18:00)" 부분집합 MAE도 함께 낸다(쉬운 밤 시간이 평균을 낮춰 보이게 하는 효과를 드러내기 위해).

## R11. 일정과 CO₂ 반응 (FR-010)

- **일정**: `config/schedule.toml`에 실습실 평일 일정(09:00 시작, 11:30 점심 시작, 13:00 오후 시작, 18:00 종료)을 적고 `source = "사용자 제공 추정 일정 (2026-10-21)"`로 표시. 주말·대한민국 공휴일은 제외(`holidays` 패키지).
- **반응 시간**: 각 일정 변화 시각(시작 2번, 끝 2번)마다 직전 30분 평균을 기준으로, 이후 CO₂가 기준보다 일정 폭(기본 ±30ppm) 이상 벗어나는 첫 시각까지의 분을 잰다. 시작 후 2시간 안에 벗어나지 않으면 "반응 없음".
- **어긋난 날**: 평일인데 오전·오후 실습 시간 동안 CO₂ 상승 폭이 작은 날(기본: 최댓값 − 아침 기준 < 100ppm) → "일정이 있었는데 사람이 없었던 날" 후보. 주말·공휴일인데 크게 오른 날 → "일정 없이 쓴 날" 후보.
- **점심시간 (사용자 제보)**: 점심에도 1~3명이 남는 경우가 있다. 그래서 11:30 "끝" 뒤의 CO₂ 감소는 작고 느릴 수 있으며, 점심 동안 외기(약 420ppm) 수준까지 내려가지 않는 것이 정상일 수 있다. 반응 분석은 점심 감소 폭과 18:00 퇴실 감소 폭을 따로 보고, 둘의 차이를 "남은 인원"의 흔적으로 해석한다. 과제 5에서는 점심을 '비어 있음'이 아니라 '적은 인원'으로 다룬다.
- **Rationale**: 일정이 추정이므로, 어긋난 날 목록이 곧 추정의 한계를 보여 준다(방학·휴강·과정 시작 전 기간 등). 과제 3의 "일정 정보의 가치"를 잴 때도 이 목록을 참고한다.
